# 文档职责与 AI 更新规则

## 唯一职责

| 文件 | 保存什么 | 何时由 AI 更新 |
| --- | --- | --- |
| `AGENTS.md` | 工程规则、阅读入口、验证要求 | 目录职责、命令或协作规则改变 |
| `CLAUDE.md` | 导入共同规则 | 入口适配改变；不复制公共规则 |
| `PROJECT.md` | 当前实现、目标、限制 | 系统能力或当前目标改变 |
| `TASK.md` | 活跃任务、验收条件、未完成项 | 任务开始、范围变化、验收完成 |
| `design/docs/DEVELOPMENT_ROADMAP.md` | 阶段顺序、依赖与阶段验收 | 交付顺序或阶段范围改变 |
| `design/docs/PRODUCT_SPEC.md` | 用户流程、行为、状态 | 产品行为改变 |
| `design/docs/ARCHITECTURE.md` | 边界、数据流、配置 | 模块、契约、数据所有权改变 |
| `design/docs/DESIGN_SYSTEM.md` | 通用视觉与交互 | tokens、组件规范改变 |
| `DECISIONS.md`、决策文件 | 选择、理由、取舍 | 出现需长期保留的决策 |
| `SKILLS.md` | 来源、触发条件、安装/镜像 | skill 集合或版本改变 |
| `.ai/handoff/current.md` | 当前任务接力点 | 阶段交接、暂停或任务完成 |
| `README.md` | 安装、启动、配置入口 | 项目使用方法改变 |

一次改动只同步相关文档。例如按钮颜色变更更新 token、组件展示和设计规范；
不会因此新增架构决策。跨端契约变更更新 schema/类型、fixture、架构说明与测试。

## 事实与预期

用户当前明确要求优先。已接受决策约束产品/架构预期；专项规范表达约定；
代码和实际运行结果证明实施状态。它们冲突时说明差异，不用修改文档掩盖缺陷。
将“planned”“implemented”“verified”分别写清。自动测试、模拟服务、真实集成、
生产环境、实际用户效果的证据不可互相替代。

## 控制上下文体积

`PROJECT.md` 保留当前事实，`TASK.md` 保留活跃队列。完整历史放入 Git、独立决策
或 `design/archive/`。交接尽量控制在一两屏，只链接有关材料。
不要要求每个 agent 每次加载全部历史、全部 skills 或全部设计稿。

## 交付前

1. 根据 diff 找到受影响的文档职责。
2. 同步行为、配置和状态；保留未验证边界。
3. 检查文档路径、双 agent 镜像及模板结构：`pnpm check:template`。
4. 有未完成任务时填写交接并执行 `pnpm handoff:check`。
